从零读懂 Cordis 核心

这份讲义对应仓库里的 vendor/cordis/src。Cordis 是 DeepSeek Harness 的插件内核：模型、工具、会话和代理循环都是挂在它上面的插件。读完这份讲义，你应该能自己走通一次 new Context()、一次 ctx.plugin()，以及一次事件分发。

它解决什么问题

一个代理程序会不断加上新能力：换模型、加工具、记日志、热更新配置。如果每个能力都互相 import 具体类，加载顺序和卸载顺序会缠在一起。Cordis 把这些能力拆成插件。插件不寻找对方的类，只声明“我需要名叫 tools 的服务”，以及“我提供名叫 counter 的服务”。框架负责：

  • 等依赖到齐再执行插件函数。
  • 依赖消失时先停掉使用者，再拆掉提供者。
  • 插件里登记的监听和定时器，随插件一起撤销。
  • 用事件让旁路逻辑包住原有逻辑，而不改原函数。

源码在 vendor/cordis/src。它是从上游 Cordis v4.0.0-rc.12 拷进来的，并有本地修改。学习时以这份源码为准，不要只看上游文档。

五个对象

对象文件你把它当成什么
Contextcontext.ts一张服务表。写 ctx.tools 就是按名字取服务。
Serviceservice.ts往这张表里登记自己的基类。super(ctx, 'counter') 之后，ctx.counter 就是这个实例。
Fiberfiber.ts一次插件运行。它有状态、配置、依赖快照，以及一份必须撤销的登记清单。
RegistryServiceregistry.tsctx.plugin() 的实现。它认出函数、类和 { apply } 三种插件。
EventsServiceevents.ts事件总线。ctx.on、ctx.emit、ctx.waterfall 都转发到它。

还有两个配角。ReflectService（reflect.ts）是 Context 代理的真正读写逻辑：属性访问会变成服务查找。LoggerService（logger.ts）提供 ctx.logger。

Context（代理）
  ├─ fiber        这次插件运行
  ├─ reflect      ctx.foo 的查找和登记
  ├─ registry     ctx.plugin / ctx.inject
  ├─ events       ctx.on / ctx.emit / ctx.waterfall
  └─ logger       ctx.logger(name)

new Context() 实际做了什么

构造函数在 context.ts。顺序是固定的，颠倒就会在安装内置服务时找不到根 fiber。

  1. 创建空的隔离表 symbols.isolate 和拦截表 symbols.intercept。用 Object.create(null)，避免继承 Object.prototype 上的名字。
  2. 用 Proxy 包住自己，handler 是 ReflectService.handler。从此 ctx.tools 不再是普通字段，而是一次服务查找。
  3. this[symbols.root] = self。所有子上下文都指向同一个根。
  4. new Fiber(self, {}, Object.create(null), null, () => [])。第四个参数 runtime 是 null，表示这是根 fiber：uid 为 0，状态直接是 ACTIVE，dispose 等于 restart。
  5. 依次 new ReflectService、RegistryService、EventsService、LoggerService。它们在构造时调用 ctx.reflect.provide，把自己登记成服务，再把方法混到 ctx 上，所以你能写 ctx.plugin 而不是 ctx.registry.plugin。
  6. 清掉根 fiber 在安装这些服务时收进来的临时 disposer，然后 return self。调用方拿到的是代理，不是裸对象。
const root = new Context()
// root 是 Proxy
// root.fiber.state === ACTIVE
// root.plugin、root.on、root.logger 已经可用

插件的三种写法

RegistryService.plugin()（registry.ts）只接受三种形状，由 resolve() 归一成一个可调用的 callback：

写法调用方式
函数 (ctx, config) => {}直接调用
类 class X { constructor(ctx, config) {} }new
对象 { apply(ctx, config) {} }调用 apply

同一个 callback 在注册表里只有一条 Plugin.Runtime。每调用一次 ctx.plugin()，就新建一条 Fiber，放进 runtime.fibers。所以同一个插件类可以在不同上下文里各跑一份。

函数和对象上可以挂：

  • inject：必须先存在的服务名。数组表示只要服务；对象还可以带给该服务的拦截配置。
  • Config：Standard Schema。启动前同步校验，不支持异步校验（resolveConfig() 会抛 TypeError）。
  • name：诊断用的显示名。

ctx.inject(deps, callback) 只是 ctx.plugin({ inject, apply: callback }) 的简写。依赖变化时，这个回调会卸掉再跑一遍。

Fiber 状态机

状态枚举在 fiber.ts 的 FiberState。真正决定状态的是 _getState() 和 _updateState()，不是到处手写赋值。

状态含义
PENDINGinject 里还有服务没到齐，插件函数还没跑。
LOADING依赖刚到齐，正在执行插件函数。
ACTIVE插件函数已返回。它 provide 的服务现在对别人可见。
UNLOADING正在按相反顺序跑 disposer。提供者会等所有依赖者卸完才拆自己的 effect。
FAILED插件函数或配置抛错。不会因为依赖后来到齐而自动重试，必须 update() 清掉错误。
DISPOSEDuid 已清空。不能再 effect()、restart()。
 
PENDING ──依赖到齐──> LOADING ──成功──> ACTIVE
   ^                      |                |
   |                      └──抛错──> FAILED │
   |                                        │
   └──────── UNLOADING <──依赖消失或 dispose ┘

切换钥匙是 epoch 字符串，由 _refresh() 计算：

epoch = revision + ":" + 每个 inject 服务实现的 uid
缺任何一个依赖 → epoch = "__INACTIVE__"

_setEpoch() 比较新旧 epoch。从 __INACTIVE__ 变成具体字符串，就 _reload()。从具体字符串变回 __INACTIVE__ 或换成另一组依赖，就 _unload()。inertia 保存这次进行中的 Promise。加载过程中 epoch 又变了，这次加载的结果不能算数，会接着卸载。

子 fiber 的构造顺序（Fiber 构造函数，runtime 非空时）值得按行读：

  1. parent.extend({ fiber: this }) 做出插件自己的上下文。父上下文不被修改。
  2. 把 dispose 登记成父 fiber 的一个 effect。父插件卸载时，子插件一定跟着卸载。
  3. 然后才 emit('internal/plugin')。观察者如果在这个事件里同步 dispose()，父 effect 已经存在，卸载不会丢。
  4. 事件返回后才检查 inject 并 _refresh()。Loader 可以在 internal/plugin 里补上依赖，所以不能提前算 epoch。

依赖是怎么等待的

插件声明 inject: ['counter'] 时，Inject.resolve 把它收成 { counter: null }。构造 fiber 时对每个名字调用 _checkImpl：

  • 当前隔离范围里没有这个服务，或提供它的 fiber 不是 ACTIVE，就从 _store 删掉。
  • 服务可以带 check()。返回假，也视为不可用。
  • 全部都在 _store 里，epoch 才离开 __INACTIVE__，进入 _reload()。

_reload() 先把当前依赖记到 committed，并把自己加进对方的 dependents。然后执行插件函数。这样提供者卸载时知道还有谁在用它。

服务要等本 fiber 变成 ACTIVE 才对别人可见。_updateState() 在进出 ACTIVE 时调用 reflect.notify，唤醒正在等待这些服务的 fiber。所以“A 提供 counter，B 注入 counter”不需要手写启动顺序：先 plugin(B) 再 plugin(A) 也可以，B 会停在 PENDING，直到 A 变成 ACTIVE。

effect 和卸载顺序

ctx.effect(fn)、ctx.on(...)、ctx.provide(...) 最终都进 Fiber.effect()。它立刻执行 fn。fn 可以返回：

  • 一个清理函数。
  • 一个解析成清理函数的 Promise。
  • 一个同步或异步的可迭代对象，逐个产出清理函数。

清理函数按登记的相反顺序执行。后登记的先撤，和括号配对一样。effect() 返回的函数本身也是清理函数：调用它只撤这一段；fiber 卸载时会撤全部。

有两个容易漏掉的不变量，都写在 effect() 和 _unload() 里：

  • 清理函数在 execute() 之前就挂进 fiber 的清单。插件函数执行到一半如果开始卸载，已经登记的部分仍会被收走。
  • 提供者的 effect 要等 provisions 上的依赖者全部卸完才拆。依赖者卸载期间仍可以读到这个服务。这就是“先停使用者，再拆提供者”。

fiber 已经 DISPOSED 或正处于 UNLOADING 时，再调用 effect() 会抛 CordisError('INACTIVE_EFFECT')。不能在拆的过程中再挂一块无人负责的登记。

五种事件

监听用 ctx.on(name, listener)。监听属于当前 fiber，fiber 卸载时自动移除。prepend: true 插到队首。global: true 不受上下文过滤。

_resolve() 在分发前做三件事：可选的第一个参数如果是对象或函数，就当成监听器的 this；取出事件名；按 Context.filter 丢掉不属于这个隔离范围的监听。服务上的 [symbols.filter] 比较的就是隔离标签，所以隔离出去的服务不会收到另一侧的事件。

方法等待停止条件适合
emit不等待，也不管返回的 Promise全部同步跑完通知。副作用不要依赖它的完成。
parallelPromise.allSettled全部结束后，如有拒绝就抛 AggregateError彼此无关的异步观察者。
serial按顺序 await返回值不是 null、false、undefined 就停有顺序的决策，可以提前结束。
bail同步和 serial 相同的“有值即停”第一个处理者生效，例如 internal/listener。
waterfall同步，由 next() 串联不调用 next() 就截断后面的人和最内层实现包住原行为：权限检查、改配置、改工具结果。

waterfall 的实现在 events.ts。最后一个参数被当成最内层的 next。监听器从外向内包起来。每个 next 只能调用一次，否则抛错。Harness 里工具执行前的 tools/pre-execute 就是这种：拒绝时不要调用 next()。

// 外层可以改结果，也可以直接返回而不调用 next
ctx.on('demo', (value, next) => {
  const inner = next()
  return inner + 1
})
ctx.waterfall('demo', 1, () => 10) // 11

事件名通过 TypeScript 的声明合并加到 Events 接口上。分发方法的参数类型来自这个接口。名字写错会在编译期暴露，而不是运行到一半才发现。

isolate 和 intercept

ctx.isolate('tools') 返回一个子上下文。它复制一份隔离表，给 tools 一个新的 symbol 标签。在这个子树里 provide('tools', ...) 不会盖住父树的 tools。两个 isolate 如果传入同一个 label，就共享这一格。子树在自己提供 tools 之前，读取会失败，不会悄悄退回父插件注入的那份。

ctx.intercept(name, config) 不换实现，只往拦截表上叠一层元数据。Service[symbols.resolveIntercept] 的合并顺序是：先放当前 fiber 注入时带的配置，再从根到近处叠祖先的 intercept。默认合并是浅层 Object.assign，服务可以换成自己的合并函数。

extend(meta) 是上面两者的底座：子对象原型链指向父上下文，meta 的自有属性盖住父属性。父对象不变。

和 Harness 的关系

Harness 启动时不是 new 一堆类，而是用 Loader 读 cordis.yml / cordis.patch.yml，对每一行调用等价于 ctx.plugin(插件, config)。因此：

  • 代理循环、会话、文件系统、模型适配器都是插件，都可以被另一行配置替换。
  • 业务逻辑应做成新插件，向 ctx.tools 登记工具，或监听 tools/pre-execute。不要改 fiber.ts。
  • 模型能看见的事实还必须写入会话日志。那是 Harness 的规则，不是 Cordis 的规则。

按文件精读

建议的顺序和停留点：

  1. context.ts 全文。短，先建立“上下文是代理”的图像。看构造函数和 extend / isolate / intercept。
  2. service.ts 的构造函数和 resolveIntercept。理解 super(ctx, name) 为什么会让 ctx[name] 出现。
  3. registry.ts 的 plugin() 和 Inject.resolve。
  4. fiber.ts 的构造函数、effect、_refresh、_setEpoch、_reload、_unload。这是核心，值得读两遍。
  5. events.ts 的 _resolve、waterfall、on。
  6. reflect.ts 的 provide 和代理 handler。确认 ctx.foo 如何落到 store。

源码里标有 学习： 的块注释和这份讲义对应，用来标出值得停下来的位置。原有 JSDoc 写的是调用契约，块注释写的是控制流为什么这样排。

自己做一遍

在一个小的 TypeScript 文件里只依赖 @deepseek-ai/cordis，不要启动整个 Harness：

  1. 写一个 Counter extends Service，super(ctx, 'counter')。
  2. 写一个函数插件，inject: ['counter']，在 apply 里 ctx.on 一个你自己声明合并进去的事件。
  3. 先 plugin 函数插件，再 plugin Counter。确认函数插件会等到 Counter 激活后才执行。可以在两边打日志看状态。
  4. 调用 root.fiber.dispose()，确认监听不再触发。
  5. 给函数插件的 tools/pre-execute 式瀑布加一个不调用 next() 的监听，确认内层没有运行。

做完这五步，再去读 packages/core/agent-loop。那里的循环是 Cordis 的一个消费者，不是另一个内核。
