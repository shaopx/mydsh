0. 一句话定位

MyDSH（DeepSeek Harness 的 fork）是一个"一切皆插件"的 AI 编程助手宿主（harness）：微内核 Cordis 只提供插件容器，模型适配、工具执行、会话存储、agent 循环本身——全部是可替换的插件，从 YAML 配置组装。

宿主（harness）之于 agent，就像 Android 系统之于 App：agent 的"智能"来自大模型，但要干活（读写文件、执行命令、联网搜索）需要一整套运行环境——这就是 harness 提供的：工具注册、权限审批、会话持久化、上下文管理。Kotlin 里最接近的类比是你写一个 Ktor Application：框架（引擎）只负责生命周期和管道，业务全靠 install() 进去的插件。

1. 分层结构：代码的物理布局

vendor/          Cordis 微内核（~8k 行 TS，源码内置而非 npm 依赖）
packages/        70+ 个 dsh-* 插件包，按领域分组
  core/            会话、agent 循环、工具注册表、系统提示组装   ← 引擎
  llm/             模型提供商适配器（llm-pi-ai、llm-deepseek…）
  shell/ terminal/ subprocess/ ssh/   命令执行域
  session/ deliverables/ spill/        持久化域
  browser-use/ computer-use/ web/    交互域
  client/          React UI 包群（ui-layout、ui-sidebar、locale…）
  api/             远程 BFF
  boot/            应用启动（profile 解析、HMR）
  util/            零依赖基础件（home-paths 就在这）
apps/
  web/             Vite 构建的浏览器端（Electron 也加载它）
  desktop/         Electron 桌面壳
这个布局相当于 Kotlin 多模块 Gradle 工程：vendor/ 是你 fork 进来自己维护的第三方库（类似把 OkHttp 源码 vendor 进仓库以获得可审计、可打补丁的掌控力）；packages/* 是 70 多个 feature module；apps/* 是最终的可执行应用模块。DSH 用 pnpm workspace 组织，等价于 Gradle 的多项目构建 + implementation(project(":xxx"))。

2. Cordis 微内核：三个核心概念

① ctx（Context）—— 服务定位器 + 生命周期宿主

每个插件启动时拿到一个 ctx 对象，它是所有服务的入口。服务通过类型化 key注册和查找：

// 插件 = 一个函数，接收 ctx，声明式列出依赖
const MyPlugin = definePlugin((ctx) => {
  // 注册是可逆 effect：插件卸载时自动撤销
  ctx.effect(() => () => console.log('cleaned up'))
  // 订阅事件也是 effect
  ctx.on('session/event', (event) => { ... })
})
ctx ≈ Android 的 Context + Hilt/Koin 的 DI 容器的合体：既能 ctx.get(SomeService) 找服务（Koin: get<SomeService>()），又携带生命周期（Android Context 的 registerReceiver 要配对 unregisterReceiver——而 Cordis 把"配对"自动化了，见下一条）。Dart 里的对应物是 Flutter 的 Widget 树 + InheritedWidget：Element 也是"挂载即获得环境、卸载即自动清理"。

② 可逆 effect —— 自动化的资源所有权

ctx.effect() 注册的清理函数在插件卸载时按注册逆序执行。这是 vendor/cordis/src/fiber.ts（778 行）的全部职责：维护"谁拥有哪些待清理资源"的所有权树。没有特权核心——官方文档原话："你通过在其他插件旁边挂载一个插件来扩展 dsh"。

这就是 Kotlin 协程的结构化并发：你在 CoroutineScope 里 launch 的任何子协程，在 scope cancel() 时自动向下传播取消——你从不需要手动记住"我启动过的每个线程都要 join"。Cordis 的 effect 同构：插件作用域内注册的每个清理动作，随插件卸载自动逆序执行。Java 程序员熟悉的痛点（try-with-resources 只管单个资源、listener 泄漏）在这里被语言级的所有权模型消解。JVM 上最接近的思想是 Reactor/RxJava 的 Disposable 链（Disposables.composite()），但 Cordis 把它做成了默认而非纪律。

③ typed events —— 编译期检查的事件总线

通过 TypeScript 的 declare module 声明合并，任何插件都能给全局事件表添加类型化事件键，全进程静态可查。

相当于给 EventBus（greenrobot/EventBus 或 Kotlin SharedFlow）的每条消息都写了 sealed class：发布 ctx.emit('agent/step', payload) 时，payload 类型、监听者签名全部编译期校验，而事件表本身可以被任意插件扩展（不需要修改总线源码）。Dart 程序员可以想象"每个插件都能向 StreamControllers 注册表添加新的强类型 Stream"。

3. 组合机制：profile → bundle → patch

这是"配置即架构"的关键。一个运行中的 MyDSH = 一棵插件树，由有序层叠出：

空的插件行列表
  + profile 声明的 bundles（有序）              ← 发布层的默认配置
  + ~/.mydsh/profiles/<name>/cordis.patch.yml   ← 用户层
  + --patch 命令行 overlay                      ← 临时层
  • profile：命名组合，web / headless / sdk / desktop（Electron 专用）
  • bundle：插件的分发格式。dsh-base 是公共底层（模型适配+工具+持久化+沙箱+凭证），dsh-web-app 在其上加浏览器应用
  • patch：按 id 定位一行插件，整个替换其 config，或插入新行
三层叠加 = Gradle 多项目构建的配置覆盖链：根 build.gradle.kts 定公共配置（bundle），子模块覆盖（profile），命令行 -Pproperty 临时覆盖（overlay）。也可以类比为 Spring Boot 的配置优先级：打包默认 < application.yml < 环境变量。DSH 的独特之处在于被"配置"的不是属性而是整个插件的挂载与卸载——我们把 llm-deepseek 的行 patch 成 disabled: true，等于在 Spring 里用 profile 条件性地 @ConditionalOnProperty 排除掉一个 auto-configuration。

我们的 LLM 配置正是利用这一点：在 ~/.mydsh/profiles/desktop/cordis.patch.yml 里 patch 掉 llm-deepseek、给 llm-pi-ai 注入 qwen-maas 网关 provider、覆盖默认模型——对上游代码零修改，纯配置层完成。验证工具：dsh --profile web --dump-config 可打印最终组合树。

4. 核心引擎：一次对话的完整生命周期

先明确两个单位：

  • step（步骤） = 一次模型请求 + 它调用的工具
  • turn（轮次） = 零或多步：从用户输入被认领开始，到"不再欠任何东西"结束
turn/start
  认领输入 + 组装提示词（快照模型选择、注入工具 schema）
  → agent/pre-step（瀑布：监听者可改写/拒绝消息）
  step/start
    agent/request → 准备调用 → 绑定适配器
    追加用户消息到会话日志 → 从日志冻结出模型历史
    流式调用 → llm/stream → agent/assistant-stream
      chunk*（增量）→ assistant/message（落日志）
    tool/call* → tools/pre-execute → 执行 → post-execute → tool/result*
  step/end
  工具还欠请求 或 新输入到达 → 下一个 step
turn/end
step/turn 的关系 = 协程与 Job 的父子关系：一个 turn 是一次用户交互的完整 Job，其中的每个 step（模型请求+工具执行）是顺序执行的子任务。而"工具还欠请求 → 下一个 step"就是 agent 的核心循环：模型回复"我需要先读这个文件"，工具执行后把结果喂回去，再来一次模型请求——直到模型不再要工具，turn 结束。

三个关键设计原则

(1) 日志即真相（Model-visible ⟺ logged）。发给模型的所有东西（system/message、user/message、assistant/message、tool/*）都是持久会话事件，落盘到 session.v4.jsonl.zstd。模型历史不是内存状态，是每次从日志推导并冻结的。

这是 Event Sourcing（事件溯源）架构：像 Kafka 的 log 或 jetbrains 用来做 IDE 撤销的命令栈——当前状态 = fold(全部历史事件)。好处：崩溃后重放日志即恢复现场；审计、回放、分支（fork 会话）都天然免费。Dart/Flutter 程序员最熟悉的同类设计是 Redux 的单一 Store + action log，或 Flutter DevTools 的 timeline 事件流。

(2) waterfall 事件（瀑布式拦截点）。agent/pre-step、llm/stream、tools/* 是瀑布：监听者必须调 next() 否则整条链短路。守卫、审批策略、遥测都挂在这里，不需要修改循环本身。

就是 OkHttp Interceptor 链或 Ktor 的 intercept 管线：每个拦截者可以改写请求/响应、可以直接短路返回（拒绝执行），也可以 proceed()（这里的 next()）放行给下一个。仓库规则"waterfall 监听者必须调用 next()"对应 OkHttp 拦截器忘记 chain.proceed 的话调用链就断了——只是这里靠文档约定而非编译器。

(3) 流式与提交分离。agent/assistant-stream 的 chunk 是进程内瞬态，只有完整消息才提交为持久事件——崩溃恢复时丢的只是未完成的流，日志永远一致。

等于 数据库事务的影子：流式 token 像 redo log 的增量写入，但只有事务提交（assistant/message 落日志）后才对外可见/可恢复。UI 拿到的打字机效果是"未提交数据的前端预览"。

5. 核心包一览

包职责ctx key
core/session追加式 SessionEvent 日志 + 内存 storectx.sessions
core/system-prompt提示词分节组装ctx.systemPrompt
core/tools作用域工具注册表 + 带守卫的执行管线ctx.tools
core/agentAgent 接口 + 活动注册表 + agent/* 事件ctx.agents
core/agent-loop默认驱动器（上面流程图的实现）ctx.agentLoop
llm/llm消息/流词汇表 + 适配器接缝ctx.llm

注意：agent-loop 自己也只是插件——理论上可以整环替换驱动器。文档明确"改 agent-loop 需要更新 architecture.md"，它是唯一接近"特权"的东西。

ctx key ≈ Hilt 的限定符注解（Qualifier）或 Koin 的 single { ... } 绑定键：服务注册时绑定一个类型化 key，消费者按 key 注入。区别在于 Cordis 的注册天然随插件生命周期可逆——插件卸载，它注册的服务/事件/工具全部消失，不留悬空引用。

6. Desktop 启动链路

MyDSH.exe (Electron)
  └ main.ts → 启动 Desktop Host（Electron Node 模式）
      └ node-environment.ts ←【我们改的】读 ~/.mydsh/network.json，
        为子进程注入 代理/CA 环境变量（文件不存在 = 零注入）
      └ 调用共享 CLI profile runner：dsh --profile desktop
          └ 组合插件树（dsh-base + dsh-web-app + ~/.mydsh patch）
              └ api server 监听 OS 随机端口
  └ 窗口加载打包好的 Web 资产（apps/web 的产物）
      └ client 插件在同一 document 激活
      └ 通过 RPC/流连接本机 Host（认证 token）

双平面结构：Host（Node 进程）跑全部 agent/工具/会话；渲染进程只跑 React UI。UI 不直接碰系统，一切经 RPC——这也是 Web 版和桌面版能共享 95% 代码的原因。

和 Flutter 的架构分工一模一样：Flutter Framework（UI）通过 Platform Channel 与宿主平台（能力）通信，UI 进程不直接碰系统 API。也像 Android 的双进程模型：前台 UI + 后台 Service 通过 Binder 通信。Electron 的 main 进程 ≈ Android 的 Application/Service 层，renderer ≈ Activity 层。

7. 我们的定制在架构中的位置

改动架构层次为什么这个位置是对的
DSH_HOME_DIR_NAME='.mydsh'util（基础件）所有路径推导的根，一处改全局生效（profile、会话、凭证全在 ~/.mydsh 下）
network.json 注入Electron Host 启动在所有子进程诞生之前注入环境，覆盖整棵插件树的网络行为；配置驱动 = 不影响直连环境
productName: MyDSH打包配置Electron userData/单实例锁/安装目录都由它派生——解决了与官方版互斥问题
LLM patch（qwen-maas）配置层（非代码）Cordis 的 patch 机制本来就是为此设计的；llm-pi-ai 是 OpenAI 兼容适配器，声明一个 provider 即接入
mitm-ca.pemextraResources跟着安装包走，network.json 用 "packaged" 引用
品牌文案locale 包 + web 标题brand.localBuild 键是 UI 显示产品名的单一出口
