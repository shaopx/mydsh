一、core/scope — 作用域原语（471 行）

解决的问题：多个 agent 并存时，事件和注册表如何按 agent 隔离，又能继承？ 比如 UI 想监听"所有 agent 的事件"，而某个 agent 的守卫只想看自己的事件。Cordis 本身不知道 agent 是什么——这个包提供纯粹的、领域无关的作用域机制。

204 行index.ts — 作用域的铸造与事件路由

ScopeKey：不透明的身份

export type ScopeKey = object

作用域的 key 就是任意对象——身份即地址，不做字符串化。谁创建谁知道，机制本身不关心它代表"一个 agent"还是"一次任务"。

JS 里 object 身份比较 ≈ Kotlin 的 Any? 引用相等（===）或一个不重写 equals 的类：每个实例天然唯一。比字符串 key 安全——字符串会撞名、会被枚举，对象引用不会。等价于 Java 里用 enum 实例或 AtomicReference 当 Map key。

createScope：铸造一个作用域

export function createScope(ctx: Context, key: ScopeKey, options?): Scope {
  const fiber = ctx.plugin(scope)               // ① 挂一个空插件 = 私有 fiber
  const scoped: Context = fiber.ctx.extend({ [kScope]: key })  // ② 给 ctx 打上作用域标签
  return { ctx: scoped, rawDispose: fiber.dispose, dispose: ... }
}

三步曲：① 在父 ctx 下挂一个空函数插件（function scope() {}）——Cordis 的 fiber 天然是一个可整体卸载的所有权单元；② extend 出一个携带作用域标签的派生 ctx——之后所有经这个 ctx 做的注册，读取时都能问出"我属于哪个作用域"（scopeOf(ctx) 沿原型链读到 [kScope]）；③ 返回 dispose，卸载即撤销该作用域内的一切注册。

ctx.plugin(scope) ≈ 协程里的 CoroutineScope(Job(parent))：空插件就是空 Job——不执行任何逻辑，只充当所有权锚点；dispose() ≈ job.cancel() 及其后的传播。携带标签的派生 ctx ≈ coroutineContext + CoroutineName(element)：上下文元素沿链可查。

bindScopeParent / scopeChainOf：作用域链

子作用域绑父作用域（有环检测、绑定一次后只有拿到 ScopeParentBinding 的原始绑定者才能 rebind）。链只有两个消费者，方向刚好相反：

  • 注册表向下继承（store.ts 的 chainLayers）：子作用域能看到祖先的注册层
  • 事件向上冒泡（scopeTarget 的 filter）：发给后代作用域的事件，祖先作用域的监听者也能收到
事件向上冒泡 = Android 的触摸事件/Flutter 的事件冒泡反过来的注册表语义；更准确的统一心智模型是 DOM 的 event bubbling + CSS 级联：样式（注册）沿继承链向下生效，事件沿树向上传播。rebind 的权限设计类似 SharedPreferences.edit() 返回编辑器句柄——能力即对象。

scopeTarget：路由型事件载体

给一个对象（如 Session）生成一个"代理监听目标"。Cordis 派发事件时会调用载体上的 [Context.filter] 谓词来决定某个监听者的 ctx 是否该收到：未打作用域标签的监听者全局收；打了标签的，只有 key 等于分发目标、或目标是其祖先时才收。事件只上不下。

267 行store.ts — 作用域感知注册表的三件套
  • NamedEntries<V>：按名唯一注册（重名抛错），插入序，insert() 返回幂等的撤销函数
  • AnonymousEntries<V>：匿名追加（同值算多条），append() 同样返回撤销
  • ScopedLayers<L>：注册表的"全局层 + 各作用域覆盖层"容器

ScopedLayers 的三个读法体现了精确的语义切割：

  • peek(scope)：只看本作用域自己的层——文档强调"chain-blind"，防止"自己的守卫设置悄悄混入祖先的"
  • chainLayers(scope)：沿链向上收集（祖先在前、自己在后，后者最终生效）
  • merge(scope, pick)：按名合并出有效视图——近者覆盖远者

effect(ctx, action) 把"往哪层写"和"写归谁清理"合并成一个决定：从 scopeOf(ctx) 读作用域，注册进对应层，撤销函数挂进 ctx.effect()——插件卸载 = 层清空 = 层对象回收，全部自动。

ScopedLayers.merge = CSS specificity 的简化版：全局样式表 + 各级 override，近处赢。NamedEntries 的幂等撤销函数 ≈ Kotlin MutableMap + 返回的 AutoCloseable；整套层随插件 fiber 卸载而消失，再次对应结构化并发"作用域即生命周期"。

二、session/types.ts — 词汇表（578 行）

整个 session 包乃至整个系统的类型地基。逐块讲：

1. 品牌化标量（Branded types）

export type SessionId = Branded<'SessionId'>      // 一个字符串，但类型上不等于 string
export type SessionSeq = BrandedNumber<'SessionSeq'>  // 一个数字，但类型上不等于 number

SessionSeq(42) 构造时校验"非负安全整数"，-0 都拒绝。仓库规则"跨边界的 opaque id 必须品牌化"防止的就是把工具调用的 seq 当会话偏移量用这类事故。

= Kotlin 的 @JvmInline value class SessionId(val raw: String) 或 Java record 包装，但零运行时成本（纯类型层）。构造函数里的校验 ≈ init { require(...) }。

2. SESSION_FORMAT_VERSION 与 SessionHeader

SESSION_FORMAT_VERSION = 4 是单调整数（无 major/minor），盖进每个新写日志的 header。升级规则极其克制：只有"现有判别器无法防止不安全解读"才 bump；未知事件类型由 ignorable 标记治理（见下）。SessionHeader 存日志之外的元数据：cwd、fork 血缘（parentSession/isSeeded）、子代理深度（delegationDepth，持久化以便重启后预算不重置）、agentPreset（持久化以防恢复出模型无法操作的组合）。

= Android 的 DatabaseInfo 版本号 + Room Migration 链，或 protobuf 的 schema 版本。ignorable 标记的设计哲学很值得抄：默认"未知=拒绝重建"（宁可过严不可瞎猜），作者显式标注"丢了也不影响解读"才允许跳过——故障模式偏向 fail-loud 而非 fail-silent。

3. SessionEventMap — 事件表（核心！）

事件含义类别
turn/start / turn/end轮次边界；end 携带 TurnEndReason（completed/aborted/blocked/error/max-tokens/interrupted/forked）边界
step/start / step/end步骤边界（一次模型调用+其工具）边界
user/message用户输入；三种来源（真人/agent.inject 注入上下文/goal 续轮）都逐字进模型，靠 source 区分表面
developer/message增量工具增删声明，靠 headerSeq 引用历史 header 里的完整定义表面
system/message渲染后的系统提示（表面节点 0），支持原地替换和归一化表面
assistant/message成型的助手消息：内嵌精确压缩流 + usage + interrupted 标记表面
assistant/attempt未成型消息的尝试（失败/重试/取消），保流不保历史——不伪造模型可见历史留痕
tool/call / tool/result工具请求与结果；arguments 是未解析的原始 JSON 字符串（模型怎么写就怎么存）表面/留痕
request/header请求完整头快照（config+tools），最新一条重建请求头仅日志
request/context路由元数据（provider/model/上下文窗口），只在变化时记仅日志
session/end-seedfork 继承前缀的切割标记（只有构造器和 buildForkSeed 可写）仅日志

三个精妙设计：

  • SurfaceOp 是条件字段：SessionEvent 是 discriminated union——只有五类"消息生产事件"能带 surfaceOp/sourceEventSeqs，编译器在 Session.append() 调用点强制。表面事件必须声明自己如何进入表面：'append'（追加到尾）或 {op:'replace', startSeq, endSeq}（替换一段范围——压缩用）。
  • ignorable 只治理未知类型，不治理任意嵌套字段变化——嵌套变化的兼容性要靠"同版本读者保留旧表示"的发布纪律。
  • PluginRecordMap：实验插件用 plugin:xxx/yyy 命名空间记日志外事件，类型声明的合并不进入已发布的持久化 schema。

三、session/index.ts — Session 与 SessionStore（1555 行）

两个角色：Session（一个事件溯源的聚合，普通类）与 SessionStore（Cordis Service，ctx.sessions）。

Session 类：日志 + 四个增量 fold 缓存

session.append(type, data, ...surfaceOpts)   // 追加（单事件或批量）
session.surface          // SurfaceManager（表面视图）
session.requestHeader()  // fold request/header 事件 → EpochHeader（增量，O(新事件)）
session.requestContext() // fold request/context
session.toolHistory()    // fold header+developer 消息 → 工具史
session.deriveMessages() // 表面 → Message[]（模型历史！）

append 是全系统最热的写入路径，安全措施层层叠：

  1. snapshotAppend：一次迭代完成 读取+校验+拷贝（"有状态的 getter 不能给校验一个值、给存储另一个值"）；非 JSON 可序列化（BigInt/循环引用/Date/Map…）当场拒绝
  2. createAppendEvent：深冻结，seq = log.length（全系统依赖的连续性契约）
  3. surfaceManager.validateNext：表面转移合法性（见下节）
  4. commit：推入日志 → 立即同步派发 session/event（观察者失败被逐个圈禁，不影响已提交事实）

批量 #appendEvents 更讲究：所有候选先全部验证、监听者快照先解析（防监听者变更中途生效）、然后一次性提交——要么全进要么全不进。持久化是插件的事：持久化插件订阅 session/event 异步缓冲，session/flush（store 的方法，await 所有监听者）是持久化检查点——热路径永不阻塞在 I/O。

Session ≈ EventStore + Aggregate（CQRS/Event Sourcing 的聚合根）。四个 fold 缓存 = @Transient 的投影缓存：日志是唯一真相，requestHeader()/toolHistory()/deriveMessages() 都是从日志折叠的物化视图，只在读时增量更新。批量 append 的"先全验后全提" = 数据库事务批量提交；监听者圈禁 = RxJava onErrorContinue / 协程 supervisorScope 的"子失败不传染兄弟"。

创建/进场/宣布：prepare → enter → announce

这不是过度设计——注释讲得很清楚：agent-loop 需要把会话生命周期折叠进 agent 自己的同一个 effect，让"agent 卸载"按顺序先发布完驱动器的收尾事件、再撤会话。三段式：

  • prepare：构建未入店的 Session（只读）
  • enter：装入 store + 安装发布钩子，返回 detach——先不广播
  • announce：广播 session/created——调用方先把 detach yield 进自己的 effect 再 announce，这样同步抛出的 created 监听者会回滚整个进场而不泄漏

便捷版 create() = 三连。另有防护：append 不可重入（entry.appending 期间再来直接拒绝）；在 created 派发完成前禁止追加；enter 后重查 id 冲突（防"prepare 后被人插队"）。

这是两阶段提交的构造学版本：先登记（enter），后对外官宣（announce），官宣失败回滚登记。对应 Kotlin 里 val scope = CoroutineScope(SupervisorJob()) 后、注册 listener 前先 try……不，更准确地：像 Spring 的 ApplicationEventPublisher + @Transactional 的 afterCommit 语义分离——"状态生效"与"事件广播"是两个可分别失败的阶段，必须能原子回滚。

fork：从一个存活会话的精确边界开分支

fork(source, boundary?, childId?)：拷贝 [0..boundary] 前缀 → 追加 session/end-seed {inherited:true} 标记切割点 → 用 openTurnClosers（repair.ts）给悬空的工具调用补合成错误结果（结果文案教模型"只读/幂等才重试"）→ 关开着的 step/turn（reason: forked）。inheritedEventCount 只数拷贝来的事件，合成的关闭器不算继承。

四、session/surface.ts — 模型可见表面（758 行）

本包最核心的抽象。日志 ≠ 模型历史：日志里全是事实（尝试、失败、边界、插件记录），但只有五类消息事件上"表面"。表面是一个有序的 seq 序列，由每个表面事件自带的 surfaceOp 翻折出来：

append:  nodes.push(seq)                        // 尾部追加
replace: nodes.splice(startIdx, len, seq)       // 区间替换（压缩的机制基础）
project: projectedMessages.set(seq, message)   // 插件投影改写既有内容（如 image/offload）

计划/应用分离是这里的主旋律：planSurfaceEvent（纯校验，产出计划）与 applySurfacePlan（提交变更）分开；SurfaceManager.validateNext 先验证候选但不改状态，事件真进日志才应用计划——失败永远不会留下半改状态。

校验规则体现了大量实战教训（每条规则都有事故背景）：

  • sourceEventSeqs 必须引用更早的事件、不得重复、且 replace 必须引用所有被遮蔽节点（否则替换来源无法追溯）
  • tool/result 的 replace 只许改 content（其余字段全等才放行）
  • 表面节点 0（系统提示）的替换必须也是 system/message 且恰好只盖那一个节点
  • isAppendSurfaceEvent 的区分服务人类可读的转录：替换副本是"模型专用"的（压缩落地会抹掉用户已看过的对话），append 原件才是人类转录的原料——一个 API 同时服务两种读者
表面 = git 的分支视图：日志是 commit 链（append-only 全量事实），表面是"当前检出的树"（rebase/压缩后的有效状态）。surfaceOp: replace ≈ interactive rebase 的 squash——不删任何 commit（历史事件全在），但有效视图里旧内容被新节点遮蔽。contentGeneration 计数器 ≈ 视图的 etag：变了就整重建派生缓存，没变就尾部增量。

五、session 的其余文件

73 行seq-ranges.ts — 编解码 seq 区间（持久化传输用），纯工具，此处展开意义不大。
92 行known-event-types.ts — 生成文件（gen-persistence-catalog.ts 产出，doc-sync 门禁校验新鲜度）。列出本构建认识的所有事件类型；读路径遇到未知类型时：有 ignorable 就跳过，没有就拒绝重建。
49 行preparation.ts — SessionPreparation：实现 JS 的 Symbol.dispose（ECMAScript 显式资源管理），把"未发布 Session 的提供方状态"包成 RAII 句柄：发布消耗状态后 dispose 变 no-op，未发布则释放。
Symbol.dispose = Kotlin/Java 的 AutoCloseable + use { }/try-with-resources 的 JS 版（using 语法）。
211 行repair.ts — 尾部修复。ToolCallRecovery 是一个小状态机：观察事件流，追踪"助手要了但没答"的工具调用；results() 为悬空调用合成保守的错误结果（文案明确教模型判断"只读/幂等才重试，有副作用先查外部状态"）。两个入口：崩溃恢复（interrupted 文案）/ fork 种子（forked 文案，提示"父会话可能在 fork 点之后完成了它"）。合成事件的时间戳复用最后一个真实事件——不发明未来时间。
69 行request-header.ts — canonicalHeader（空 tools 折叠为缺省——"canonical"意味着整个系统只有一个表示法）、headerEquals（逐字段比较，tools 用 JSON 串比较）、foldRequestHeader（离线折叠；Session.requestHeader 是它的增量版）。
75 行tool-history.ts — ToolHistoryProjection：折叠 header + developer 消息得到工具史（基线工具集 + 历次增删），供"支持工具增删能力的适配器"在请求里投影历史定义；遇到旧日志（header 无配对 updates）自动退化为"只给当前激活集"。
30 行fork.ts — buildForkSeed：切片 + 标记 + 调 repair 的 closeTurnClosers 收尾。fork 的全部魔力就这 30 行。

六、本篇要点

  1. scope 用 471 行解决"多 agent 隔离与继承"：注册表向下继承、事件向上冒泡、空插件当所有权锚点——全部建在 Cordis 的 fiber/ctx 上，没有发明新生命周期。
  2. session 是事件溯源的教科书实现：append-only 日志是唯一真相；表面/fold 缓存全是派生物；持久化是插件订阅，热路径零 I/O。
  3. 处处计划先行、失败无痕：先验证再提交、批量要么全进要么全不进、校验用一次迭代防止 TOCTOU。
  4. 兼容性治理成体系：版本号单调、未知类型必须 ignorable、canonical 形式唯一、repair 的合成事件连时间戳都不发明。
