system-prompt 与 tools：提示组装与工具管线

本篇覆盖模型请求的两大输入面：提示词从哪来（system-prompt，700 行单文件）和工具怎么定义、怎么被安全地执行（tools，3797 行、10 个文件）。

一、system-prompt：有序分节注册表（src/index.ts，700 行）

解决的问题：系统提示不是一整段字符串，而是几十个插件各自贡献碎片、按序拼装、每次模型步骤重新组装。这个包提供一个 Cordis Service（ctx.systemPrompt），管四类注册：

注册项方法说明
节（section）section()系统提示的正文碎片，order 排序；可静态文本或函数；complete: true 表示"我是完整提示"（多个 complete 同时激活则报错）
动态上下文context()运行时快照（工作目录、沙箱策略、审批策略……），以 user 消息形式注入；required: true 的不会被抑制
变量variable(){{name}} 插值源，每次组装求值
工具 schematools()Provider 每次组装返回本步可见的工具 schema

三个关键设计

(1) 顺序是治理问题，不是细节。 包里有一个 65 项的 SECTION_ORDERS 中央分配表（HARNESS_IDENTITY=-1000、各工具 1000~3000、PERSONA 后缀 10200……）。每个仓库内插件通过 getSectionOrder('TOOL_READ') 领自己的位置——提示里谁先谁后跨包协商，而不靠数字魔法。

这个分配表 = Android 的 Broadcast priority 或 Netty 的 handler 顺序表：多插件共写一个产物时，顺序必须有个"户口管理处"。没有它，两个插件各写 100 就冲突了。

(2) 组装流程（assemble）。 变量求值（全局先、沿作用域链近者覆盖）→ 分节合并（同名 shadow）→ 工具 provider 求值 + toolOrder 排序（配置可指定顺序，必须含 <unlisted-tools> 锚点，未知名报错）→ 瀑布 system-prompt/assemble 让监听者可改写 → 若有 complete 节则在瀑布后恢复为唯一节（瀑布不能冒名顶替完整提示）。

(3) 严格插值（renderPrompt）。 {{var}} 是严格的：未知变量、未赋值、畸形引用——全部抛错，绝不静默留空。连"孤立的 {{ 后面没有 }}"都区分了"后面还有 }}（畸形，报错）"和"就是字面文字（放行）"。防的原型链污染也有：Object.hasOwn 检查。interpolate: false 的节保留字面文本。

vs. 模板引擎的 "missing key 渲染成空" 行为——这里反其道而行：fail-loud。因为系统提示里的空变量不是显示问题，是模型行为问题（模型会看到空洞的指令）。教训都写在错误消息里。

另有 refreshContext(assembly)：工具批次中途想刷新运行时事实（如用户改了审批策略），只重求 context providers，不重跑分节/工具/变量——承认的部分不回锅。

二、tools/index.ts：注册表与视图解析（412 行）

ToolsService（ctx.tools）管三样东西，全部用第 02 篇讲的 ScopedLayers 承载：

  • 工具注册（ToolLayer.tools）：register(definition, {when})。注册时即校验 output 声明（schema/render 必备）、JSON Schema 子集合法性、timeoutMs。保留名 run_code 直接拒绝（PTC 传输名）。
  • 限制（restriction）（ToolLayer.restrictions）：restrict({allow?, deny?}) 只能作用于全局工具、只能在 agent 作用域里调（全局限制会罩住所有 agent——报错消息直接教你去给目标 agent deny）。多条限制相交；空过滤器和未知名都报错（"空过滤器几乎总是物化为空的配置 bug"）。
  • 守卫（guard）（独立 GuardLayer）：guard(fn) 单调否决——只能拒绝，不能批准，所以监听顺序无法把"拒绝"变回"允许"。

view(scope)：一次遍历解析完整视图

核心私有方法，规则：

  • 全局 + 祖先作用域的注册作为继承集，本作用域自己的注册豁免所有限制
  • 限制沿链全部相交（layers.every(layer => layer.admits(name))）
  • 近的 shadow 远的；被限制掉的全局工具读作"不存在"
  • 同时产出 knownNames（限制前全集，给 toolOrder 校验）和 restrictableNames（给 restrict 校验）
= CSS 的"文档级样式 + 更具体选择器覆盖"+ Android 权限的"默认拒绝 + 显式清单"。守卫的单调性（只否不许）= 安全审计原则：拒绝不可被后续步骤翻案。

resolve 与 ResolvedToolSet：步骤级激活

注册可带 when(context) 条件（agent + 本步模型选择 + 取消信号）。resolve() 在步骤开始时一次性解析全部条件，产出冻结的 ResolvedToolSet：之后 view(scope) 只对"仍以同一注册可见"的已准入项放行——中途卸载的工具不会被迟到的条件结果复活。取消时无部分选择发布（先 throwIfAborted 再全量提交）。

执行器接缝（ToolExecutor）

setExecutor() 注册"工具执行器"（native 本进程执行 / PTC 程序化传输，每作用域至多一个）。执行器可带提示节（sections），由 registry 代为注册成 system-prompt 节，且文本函数运行时先自检"我仍是当前 scope 选中的执行器"——执行器卸载后其提示节自动渲染为空。卸载时把 record.executor 置 undefined 而非删记录：让"不可用"状态显式存在，调用落不下去也不会静默换人（ToolExecutorUnavailableError）。

三、tools/events.ts：四个扩展点（58 行）

全部是声明合并到 Cordis 事件表的类型声明，每个事件的 JSDoc 就是契约全文：

事件模式语义
tools/pre-execute瀑布allow / deny / cancel / ask（升级为人工审批）。异步闸门必须观测 exec.signal
tools/execute瀑布（环绕）超时、重试、度量的挂点。包装者可换 signal，但"调用身份不可变"；registry 会把原始取消信号重新熔断进去（防包装者割断调用方取消）
tools/post-execute瀑布accept / 替换投影 / block（把矫正反馈变成错误结果），可附加 additionalContexts
tools/resultemit观察冻结的最终结果，监听失败被圈禁
三段瀑布 = OkHttp 的 applicationInterceptors（pre）+ networkInterceptors（around）+ 出站改写（post）；ask = OkHttp 里没有的东西，更像 Android RuntimePermissions：策略升级到人工批准。signal 重熔断 = Kotlin 里 withContext(NonCancellable) 的反面：框架保证父取消一定传导到工具体，包装者换不掉。

四、tools/contracts.ts：契约词汇（418 行）

纯类型 + 少量错误类，但每条都值得读：

  • ToolDefinition：schema + execute + 必备 output（schema/render/presentationMeta）。工具体只返回 JSON value，渲染成 ContentBlock 是 output.render 的事——把"值"和"展示"分离，让结果可校验、可重放
  • 三段内容钩子：projectContent（post-execute 前）/ finalizeContent（最后一步，必须全函数不抛）/ presentCall/presentResult（UI 卡片，纯函数——会话日志重放时会再调一遍，所以不得有副作用）
  • isConcurrencySafe：只有显式 true 才允许并行；声明它即断言"会转发 signal、能达到静默"——opt-in 契约写在注释里
  • 取消语义：TOOL_ABORTED（体已启动）/ TOOL_ABORTED_BEFORE_DISPATCH（体未启动）两个规范码——重放和恢复逻辑靠它们区分"结果未知"和"根本没跑"
  • PreToolDecision / PostToolDecision：封闭 union，post 的 accept "value 和 content 二选一"由两个互斥变体编码（编译器拒绝同时给）
  • 错误类全部继承 HarnessError 带 code：UNKNOWN_TOOL、INVALID_TOOL_OUTPUT、TOOL_CONTEXT_UNAVAILABLE——可路由、可判定

五、tools/pipeline.ts：共享执行管线（807 行）

ToolExecutionPipeline——所有执行器共享的"政策机"。三段式调度：prepare() → dispatch() → complete()。为什么分三段？因为批量调度器需要先对全部调用跑完前置政策（prepare），再决定并发排布，然后逐个跑体（dispatch），最后按模型顺序结案（complete）。

prepare：身份铸造 + 前置政策

  1. createExecution：参数一次 snapshotJsonValue（防有状态 getter 的 TOCTOU）+ 深冻结；铸造 Symbol token；捕获 finalizer/projector 在参数 getter 跑之前（getter 可能干任何事）
  2. 取消检查 → tools/pre-execute 瀑布 → ask 走审批接缝（ctx.get('approval') 机会主义获取——没组审批服务就降级为 deny，agent 缺失同样降级）→ 守卫检查 → 再查取消
  3. 每一步失败都有明确归宿：政策异常 → final-result 错误；executor 拒绝但调用方已取消 → 取消优先于拒绝（记录的是 aborted 而非 denied）

dispatch：环绕 + 体执行 + 信号熔断

瀑布 tools/execute 包住 dispatchToolBody。信号熔断（fuseToolSignals）是本文件最精巧的 20 行：包装者换上的 signal 和原始调用方 signal 手动双向联动（不用 AbortSignal.any 嵌套，dispatch 结束即拆监听器）。承诺：取消永不放弃已启动的体——启动的 promise 一定跑到静默，之后结果才被改写成 ABORTED。错误分类：取消后抛出的"无身份"错误（signal.reason 或裸 AbortError）归一化为 ABORTED 码但保留消息；HarnessError 和其他错误原样保留。

三段式 = OkHttp 的 executedCall 生命周期（enqueue → run → complete）+ 数据库连接池的"借出/归还"。bodyInvoked 标志 = JVM 的 Thread.interrupt 语义（ cooperative，不硬杀）：框架不 kill 你的线程，但你必须观测取消并在完成后让框架把结果归类为"中止"。信号熔断 ≈ Kotlin coroutineScope + Job 的 parentChild 关系——子取消不影响父，父取消必达子。

complete：post 政策 + 双重物化 + 冻结发布

projectContent → postExecute 瀑布 → 取消替换（只替换成功结果；工具自身错误保留）→ finish()：先物化结果、再跑 finalizeContent、再物化一次、Object.freeze(exec) 后 emit tools/result。两段 try/catch 确保"物化失败也变成错误结果"而不是炸穿管线。canonicalResults WeakMap 用 token 认证"registry 规范化过"的结果——包装者仿造的结果会被 normalizeDispatchResult 重新过一遍 output 契约校验。

六、tools 其余文件

285 行batch.ts — executeToolBatch：一个步骤内多个工具调用的调度器。独占调用形成栅栏；并行调用进有界滚动池、启动前重新分类（防止独占调用饿死）。政策与结果保持模型顺序，只有 dispatch 可重叠。中止给跳过的调用合成错误结果（重放合法性），内部失败先排空再抛 ToolBatchExecutionError（带 partial）。
= Kotlin coroutineScope 里混合 launch（并行）与顺序 await（栅栏）的调度器，外加"取消也要凑齐每调一果"的账本纪律。
646 行schema.ts — 仓库自己的类型安全 schema DSL（z.string() 风格）+ defineTool 辅助：让工具作者用类型正确的 spec（string enum 就得是 string 数组）写 schema，编译期防手滑；再投影成模型可见的 ToolSchema（白名单字段）。
= kotlinx.serialization 的 @Serializable + 自研 validator，或 Kotlinx JsonObject builder 加类型。类比 Ktor 里用 ContentNegotiation + 数据类替代手写 JSON。
656 行json-schema.ts — 强制 JSON Schema 子集：只接受能真正 enforcement 的关键字（单 type、properties/required、items、标量 enum/const、exact-one oneOf），不认识的关键字拒绝而不是接受后不校验——"假装校验"比"不校验"更危险。工具输出、PTC 类型、subagent、workflow 共用这一套。
102 行executor.ts — ToolExecutor 接口（describe + execute 一个完整批次）与两个错误类。批次协议：一 call 一 result、输入顺序返回、绝不在有活没干完时 settle。
389 行presentation.ts — 提供方中立的 UI 卡片词汇：ToolCallView = generic / terminal / diff 三种标记意图 + FileLocation（跟随跳转）+ 文件差异。工具声明"我这通调用是编辑文件"的方式是打 tag，而不是客户端去特判工具名——所以新工具零客户端改动就有像样的卡片。
24 行error-codes.ts — 审批三态错误码（REJECTED/CANCELLED/UNAVAILABLE）。持久化契约：只比字符串，不 re-export。

七、本篇要点

  1. system-prompt 是注册表 + 组装器：分节/上下文/变量/工具四类贡献，严格插值 fail-loud，顺序由中央分配表治理。
  2. tools 注册表的三层隔离（scoped shadow / restriction 相交 / guard 单调否决）全部建在 scope 包的 ScopedLayers 上——第 02 篇的原语在这里第一次大显身手。
  3. 执行管线是三段式状态机（prepare/dispatch/complete），贯穿三条铁律：取消永不放弃已启动的体（但也不认账为成功）、值与展示分离（输出契约校验）、物化即冻结。
  4. 审批（ask）是机会主义接缝：没组服务就降级为 deny，绝不静默放行。
