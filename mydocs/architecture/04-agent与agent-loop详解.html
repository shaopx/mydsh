agent 与 agent-loop：注册表与驱动器

这是整个系统最核心的两包。agent（1802 行）定义"Agent 是什么"和注册表；agent-loop（2155 行）是默认驱动器——第 01 篇那张 turn/step 流程图的实现本体。两者通过 AgentFactory 接缝解耦：注册表不知道怎么造 Agent，驱动器注册自己为工厂。理论上可以整体换掉驱动器。

一、core/agent：注册表、工厂接缝、发起者

690 行index.ts — AgentRegistry 服务（ctx.agents）

AgentFactory：谁造 Agent？

AgentRegistry 自己不造 Agent——通过 setFactory() 接收工厂（就是 agent-loop），create()/resume() 委托过去。消费者（如 ACP 桥）只依赖 ctx.agents 接口，不 import 具体的 loop 包。接口放在 agent 包、实现放在 agent-loop 包——典型的接口与实现分离（依赖倒置）。

= Java 的 ServiceLoader + Executor 模式：registry ≈ ExecutorService（管注册与查询），factory ≈ ThreadFactory（管构造）。也像 Hilt 的 @Binds：接口和 impl 分模块，消费方只见接口。

enter/announce：又一组两阶段发布

与 SessionStore 相同的手法（第 02 篇），语义也一致：先入店（enter，返回 detach），后广播（announce，agent/created 是 serial 模式——顺序 await，一个监听者失败则创建失败回滚）。嵌套细节同样讲究：detach 发生在 created 派发中途时延迟到派发收束，保证"每个观察过创建的监听者必能看到配对的 disposed"。

发起者（Initiator）：进程内因果归因

这是 agent 包最特别的设计：withInitiator(agent, op) 用 AsyncLocalStorage 把"哪个 Agent 发起了这条异步链"沿 Promise 链隐式传播；currentInitiator() 读它，requireInitiator() 强制要求有。典型用途：深处的基础设施代码（遥测、审计）想知道"我这是在替哪个 Agent 干活"，而不想给每层 API 加 agent 参数。

但文档同时泼冷水：存在 ≠ 活着 ≠ 授权——ambient 归因只用于日志/度量，主体与所有者仍必须显式传递（worker/进程/持久化/网络边界处 ambient 语义全部失效）。还有 withoutInitiator()：建共享定时器/队列泵时清除继承，防止"第一个碰巧初始化它的 Agent"意外拥有一段共享基础设施。关闭期 disposeInitiators 排空全部在途边界后才 disable。

= Kotlin 协程的 CoroutineContext 元素传播（如 CoroutineName/MDC Context）——launch 的协程自动继承上下文；withoutInitiator ≈ Dispatchers.Default + EmptyCoroutineContext 起"无主"协程。AsyncLocalStorage 是 Node 的 ThreadLocal，但跨 async 边界。"存在不是授权"的告诫对应安全原则：ThreadLocal 里的用户身份不能当鉴权凭据用。
432 行runtime-types.ts — Agent 接口与 agent/* 事件表

Agent 的完整行为面（声明合并进 Agent 接口）+ 全部事件契约。要点：

  • 四种输入通道：followup（新轮次）、steer（塞进下一个 step 边界——运行中生效）、inject（注入上下文，不唤醒）、通用 send(target, wakeup)。inbox 持久化为 agent/inbox/spliced 会话事件——排队中的消息崩溃不丢。
  • 状态只有两态：idle ⇄ running（maintenance 对外也是 idle）。取消带 cause（user/parent/hook/disposed），keepInbox 选项保留未开工的工作。
  • 事件表的 @mode 注释就是调度语义：agent/created serial（顺序待 await）、agent/pre-step waterfall（可拒绝/改写）、agent/request-error waterfall（可接管重试）、agent/turn-stopping serial（可反对关轮——反对的方式是 steer 进新输入）、agent/assistant-stream emit（瞬态流帧）。
  • agent/request 已标 @deprecated：模型/推理力度应走 agent.model.select()——新旧扩展点的交替现场。

二、agent-loop/index.ts：工厂与生命周期事务（844 行）

FactoryOwnership：工厂级所有权账本

class FactoryOwnership {
  track(dispose)          // 记录每个存活 agent 的 teardown
  trackStartup(job)       // 记录配置启动工作
  dispose()               // 全部排空，收集失败抛 AggregateError
}

插件卸载时，所有它造的 agent + 所有在途启动任务都要排空到静默才能收尾；多个失败聚合成一个 AggregateError（不吞任何一个）。

initializeAgent：一场严密的创建事务

这是全包最难也最精彩的函数。从已获得的 Session 到发布 Agent，回滚覆盖全程：

  1. 熔断两个 abort 源：调用方 signal + 工厂 teardown → 一个 AbortController
  2. 逆序 teardown 计划（memoized，所有竞争的所有者 await 同一个静默）：停机器 → 撤作用域 → 排空并关闭持久化写柄 → 离开两个注册表 → 释放簿记。失败收集不吞
  3. 用一个生成器 effect 把生命周期钉在 owner fiber 上：yield created.scope.rawDispose; yield () => teardown()——yield 的顺序就是卸载顺序，这是 Cordis "exact disposer identity" 规则的实战（yield 包装函数会让 teardown 变成并发兄弟而非有序子步骤——注释里写了后果：agent 在最后一个轮次还在排水时就被注销）
  4. 发布序列（在 runMaintenance 里跑，占住 idle 相位）：补存未入库事件 → session.enter+announce → setup 回调（可返回同步 commit()，在发布前再校验一次）→ agents.enter+announce → ready
  5. 任何一步失败：cancel({kind:'disposed'}, {keepInbox: true}) + 全量 dispose——已提交的 session 事件保留，排队的输入不丢
这就是 结构化并发的生命周期版：Kotlin 里你写 withContext(supervisorJob) { try { … } finally { cleanup() } }，但这里的"finally"要跨 两个注册表 + 持久化写柄 + Cordis fiber 树 保持全序。生成器 yield 定序 teardown ≈ Kotlin CoroutineScope 里 child job 的注册顺序决定取消顺序——顺序是语义，不是实现细节。

resume：崩溃修复在现场

resumeWith 的读路径藏着第 02 篇 repair.ts 的调用现场：先拿写所有权（排除并发同 id resume）→ 冷读全量日志 → interruptedTurnClosers 为崩溃尾巴合成关闭事件（悬空工具补错误结果）→ 以 repair 后的日志为 seed 构造 Session。取消与所有者卸载全部用 AbortSignal.any 熔断，后到的值（如 handle）通过 releaseAbandoned 回调释放——取消不泄漏晚到的资源。

配置化 agent

Config 的 agents[] 支持启动时创建/恢复 agent（cordis.yml 声明式）。身份可以由 launcher 通过 CONFIGURED_AGENT_IDENTITIES_KEY 注入（这样 overlay 改模型路由不会弄丢会话身份）；resume 不存在的 id 只在 SessionPersistenceNotFoundError 时降级为 create，损坏和冲突保持响亮。

三、agent-loop/agent.ts：状态机本体（751 行）

Phase 状态机：idle / maintenance / running

type Phase = { kind: 'idle'; lastTurn } | { kind: 'maintenance'; abort; lastTurn; wakeRequested }
          | { kind: 'running'; abort; turn; step; wakeRequested }

外部只见 idle⇄running。wakeRequested 是闩锁：维护中/已中止的驱动收到唤醒请求时存起来，收敛到 idle 时重放。取消永远先 clear inbox（除非 keepInbox），再 abort——"队列持久化失败不得阻止已许可工作的取消"。

turn()：一轮的完整骨架

append('turn/start') → 循环 {
  preStep(target)                    // 认领 inbox + 组装 + 瀑布
  reject → turnEnds=blocked，无 step
  空消息且 step=0 → completed（花了边界但没花模型调用）
  append('step/start')；ToolCallRecovery 随听 session/event
  stepEnd = await step(decision)     // max-tokens 粘性：后续 completed 不降级
  异常 → 补记悬空工具结果再抛
  append('step/end')；toolSet.dispose()
  turnEnds 且 nextStep 空 → serial('agent/turn-stopping') → break
  target = 'next-step'
} finally { append('turn/end', reason) }
还有排队输入 → 重开一个 turn（新 AbortController）

每个出口都落一个结构化的 TurnEndReason；中止/错误/失败分别成型；throwError 先 emit agent/error 再抛给驱动边界圈禁。turn-stopping 的反对机制：监听者想续就 agent.steer() 塞新输入，机器重读 inbox——"数据决定，监听顺序改变不了结果"。

preStep 与 step：前两篇全部汇合

preStep：认领 inbox（model.current() 无选择直接报错）→ tools.resolve()（第 03 篇的步骤准入）→ systemPrompt.assemble()（第 03 篇组装）→ agent/pre-step 瀑布（拒绝/改写）。

step 的每次模型请求（while true，重试可再来）：

  1. prepareRequest：agent/request 瀑布（已弃用但仍跑）只许改控制项——试图改 provider/model/effort 直接抛错（错误消息教你用 agent.model.select()）
  2. refreshContext 刷新运行时事实 → systemPrompt 投影决策（in-history 路由 vs 归一化）→ system/message 提交
  3. 首次尝试才提交认领的用户消息（重试不重复提交）
  4. buildRequest：header 三态记录（initial/resume、change、series）+ 工具增减自动生成 developer/message（模型可见的工具演化史）→ messages = session.deriveMessages() 冻结 + toolHistory → 不可变请求对象
  5. 流式：chunk → AssistantStreamAttempt（瞬态帧 emit + 持久累积），成功 settle 成 assistant/message，失败 settle 成 assistant/attempt；中止时已交付的前缀 finalize 成 interrupted 的 assistant/message（UI 已显示的内容不凭空消失）
  6. 失败 → agent/request-error 瀑布，监听者可接管重试（{kind:'retry'} 不调 next）
  7. 无工具调用 → completed；有 → tools.execute() 整批（第 03 篇管线），additionalContexts 塞回 next-step，concludesTurn 让工具终结轮次
ReactLoopAgent 之所以叫 React：驱动核心是"事件（inbox/工具结果）→ 重算（组装/派生）→ 提交（append）→ 再看有没有新事件"的循环，像 React 的 setState → render → commit。turn-stopping 的"数据决定"= React 的"状态是唯一真相，不在事件里改状态"。整个 step 函数就是一张教科书级的状态转移表，每一行的 catch/finally 都对应一个真实的事故场景。

五、本篇要点

  1. 接口与实现分离：agent 包定义 Agent/工厂接缝/事件表，agent-loop 实现；替换驱动器理论上可行，"改 agent-loop 要改 architecture.md"是它唯一的特权。
  2. 生命周期是一等公民：enter/announce 两阶段、逆序 teardown 计划、yield 定序、失败收集不吞、取消不泄漏晚到资源——四篇里反复出现同一套纪律，这里达到顶点。
  3. 一切模型可见的东西都过日志：请求从 deriveMessages() 冻结，工具增减生成 developer/message，连排队输入都是事件——这是第 02 篇"日志即真相"的完全体。
  4. 扩展点全部数据化：pre-step 拒绝/改写、request-error 接管重试、turn-stopping 用 steer 反对、工具 concludesTurn 终结——插件改变行为靠数据而不靠顺序。
