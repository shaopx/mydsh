llm：适配器注册表与流式调用词汇

packages/llm/llm（4086 行、12 个文件）是模型调用的中立词汇层：消息与内容块的规范类型、流式 chunk 词汇、适配器注册表、以及一个 waterfall 可拦截的流式调用 API。我们配置的 qwen-maas 网关（llm-pi-ai 插件声明 openai-completions provider）最终就落到这里被调用。

一、LlmRuntime 与适配器注册表（index.ts，1204 行）

LlmAdapter：抽象基类，唯一必须实现的是 stream

export abstract class LlmAdapter {
  providerInfo(provider)            // 显示元数据（默认 id=名字）
  providerRetryPolicy(provider)     // 该路由的重试策略
  imageRequestPricing(...)          // 图像计价（token 表用）
  listModels(provider)              // 可发现模型目录（GUI 用）
  resolveModel(provider, model)     // 单模型元数据
  prepareCall(provider, model)      // 绑定"一代"适配器的调用（默认=resolveModel+stream）
  abstract stream(options)          // 唯一必须实现的方法
}

每个 provider HTTP 请求必须带 attributionHeaders()（产品 User-Agent 归因，见 attribution.ts）——契约要求在 wire 请求或库钩子里证明加了头。

= OkHttp 的 Interceptor + Call.Factory，或 JDBC 的 Driver/Connection：registerAdapter(providers, adapter) ≈ DriverManager.registerDriver；llm-deepseek、llm-pi-ai 就是两个"驱动"。Kotlin 开发者最熟悉的对应是 Ktor 引擎抽象：核心只认 HttpClientEngine，CIO/OkHttp/Netty 各自实现。

注册的三张表

表注册方法语义
adaptersregisterAdapter(providers, adapter)路由 → 适配器。all-or-nothing：任一路由已被占则整批拒绝。返回 handle 可 replace(next[]) 原子换路由集（校验全过才提交，单同步段交换，观察者看不到缝隙）
directoryregisterConfigurableProviders(entries)"可配置 provider"目录：声明本插件能通过配置激活的路由（ dormant 也列出来——Models 页展示的就是这张表）
discoveriesregisterModelDiscovery(ns, fn)按 settings 命名空间的端点探测：给一个 baseURL+凭证，问出可用模型列表（discoverModels，Remote 可跨进程）

三张表每次变更都 emit llm/adapters-updated（逐监听者圈禁——注释再次记录了 Cordis emit 用 Array.map、一个同步抛会饿死后续监听者的事实，所以这里手动圈禁）。llm-pi-ai 的"休眠"机制正是 directory 有声明、adapters 无路由；settings 写入 provider profile 后它 replace() 进路由表。

llm/stream 瀑布：全系统的模型调用都可拦截

'llm/stream'(options, next): AsyncIterable<StreamChunk>

每次流式调用（不管 loop 发的还是插件手工发的）都过这个瀑布：可短路（自己产 chunk——重放/mock）、可包 next()（重试/路由）。LOOP 构建的请求带 markAgentLoopRequest 身份且深冻结（改就抛）——因为它必须是会话日志的纯函数（"可重建性"铁律的运行时强制）；手工调用不带标记，调用方自己负责不可变。

二、prepareCall：一次绑定的调用

第 04 篇 agent-loop 的 step 每次都走 ctx.llm.prepareCall(config, signal)。看它的实现，五个要点：

  1. 绑定注册：捕获 registration（adapter + retryPolicy），后续 dispatch 用捕获的这一代——settings 中途变化不会让"这代的元数据"配"那代的端点"
  2. adapterDefaults：调用方没给的 reasoningEffort/maxTokens，适配器解析后补上——并在 header 里记录"这是适配器补的而非调用方给的"（第 02 篇 requestProposal 反向剥掉它们）
  3. 上下文窗口、输入模态、systemPromptUpdate/toolUpdate 能力随调用解析冻结
  4. stream() 只许 dispatch 一次，且 options 的 config 与 prepare 的完全相等——防"准备一套、发另一套"
  5. 没有注册的 provider → NO_ADAPTER（agent-loop 有兜底分支：中间件可以服务未注册路由，但终派发必须有适配器）

另有 forAdapter()：发给适配器前，把属于其他适配器路由的 replayState 剥掉（不同 provider 的私有重放数据互不污染）。

prepareCall ≈ OkHttp 的 Call 对象：newCall 时解析路由/DNS/超时，execute 只能一次；更贴切的是 数据库 PreparedStatement——准备时绑定计划，执行时校验参数一致性。adapterDefaults 的"标注来源"哲学 ≈ Android 里 Bundle.containsKey 的教训：分不清"用户没设"和"默认了"是无数 bug 的根源。

三、词汇文件

608 行types.ts — 规范词汇。ContentBlock 闭合 union：text / reasoning（思考过程独立于可见文本）/ image（角色中立、attachment 引用、offload 占位）/ file（永不原生发给 provider，组装时投影成确定性句柄文本，日志保留结构引用）/ tool-call / tool-result / tool-addition / tool-removal。LlmFailure 是可序列化事实（message/code/status/retryAfter/requestId/offloadImages）。MessageSourceMap 是可合并扩展的"消息来源"表（model/tool/system-prompt/runtime-context/tool-registry…插件可加）。
319 行message.ts — Message 值类型与构造器（createUserMessage 等，全部走规范化+冻结）。
510 行content.ts — 内容块结构助手：文件→文本投影、图像→文本模型投影、工具增删投影（决定"这个 provider 能不能看见这类块"的守门逻辑）。
76 行brand.ts — 本包拥有的品牌 id（ToolCallId、ProviderRequestId 等）。
ContentBlock union ≈ Kotlin sealed class 层级 + 每个变体一个 @JvmInline 值类；"文件永不原生上 wire"≈ 聊天协议里把附件换算成占位符文本、原始引用存数据库的常见设计，但这里把"投影规则"集中到了一个文件而非散在各 adapter。

四、流文件

208 行assembler.ts — BlockAssembler：chunk → 内容块的唯一规范组装算法。agent-loop 用它装配 assistant 消息的同时记录原始 chunk（重放保真）。"单一算法"意味着每个 provider 的流式差异在 adapter 内部就被抹平，loop 一套代码面对所有 provider。
533 行assistant-stream.ts — 一次流尝试的无损紧凑表示（AssistantStreamRecord，就是 session 日志 assistant/message 里嵌的那个 stream）+ 不物化成员的记录级读取器（比如"usage 是多少"不用展开整条流）+ expandAssistantStream 校验展开。
109 行adapter-failure.ts — 适配器抛出值的归一化：任意 thrown → LlmFailure（第 03 篇 pipeline 的 toolErrorMessage 的 LLM 版）。
AssistantStreamRecord ≈ proto 的紧凑编码 + lazy 解码：磁盘上存增量、读取端按需回答；BlockAssembler ≈ Kotlin Flow 的 scan 累积器——增量进、规约出，且全仓库只有一份实现，两个消费者（UI 直播 + 持久重放）看到必然一致。

五、其余文件

call-config.ts（95）LlmCallConfig（provider/model/effort/采样控制）+ callConfigEquals + markAgentLoopRequest 身份标记
retry-policy.ts（201）provider 自有重试策略的解析与校验（llm-retry 插件消费它）
error.ts（233）失败码表（AUTH/RATE_LIMIT/NO_ADAPTER/IMAGE_OFFLOAD_REQUIRED…）+ LlmError（HarnessError 子类，failure 字段保留可序列化事实——fromFailure 可把任何 provider 的失败按原 code 重新抛出）
attribution.ts（90）产品 User-Agent 归因——所有 provider 请求必须带的非密身份，防各 adapter 漂移

六、本篇要点 + 系列回顾

  1. llm 是词汇 + 注册表，不是客户端：HTTP 细节全在 adapter 插件里（llm-deepseek、llm-pi-ai），核心只管路由、绑定、词汇和可拦截性。
  2. prepareCall 的"绑定一代"语义是动态配置安全的关键：解析与派发之间世界变了，也不会混用两代元数据/端点。
  3. 单一组装算法 + 无损流记录：直播与重放必然一致，这是"模型可见 ⟺ 可从日志重建"在流式层面的兑现。

系列回顾（02–05 五个包，~1.2 万行）

包一句话
scope注册向下继承、事件向上冒泡的作用域原语（空插件=所有权锚点）

五篇合起来就是一句设计哲学：把"谁在什么范围内贡献了什么、何时撤销"做成语言的根基，其余一切都是数据流经它。
