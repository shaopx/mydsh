一、Node.js：V8 出了浏览器沙箱

Node.js = 把 Chrome 的 JS 引擎（V8）抠出来做成的通用程序运行时——一个 C++ 程序里嵌了 JS 虚拟机，再配一套能干实事的标准库（fs/net/http/child_process）。它不是浏览器：没有网页、没有 DOM。

Node 之于 JS = JVM 之于 Java。逐层对上：V8 ≈ HotSpot（JIT 执行引擎）；libuv ≈ 强制版 Netty EventLoop（异步 IO 运行时）；Node 内置模块 ≈ JDK；Node 发行版 ≈ JRE；npm/pnpm ≈ Maven/Gradle。

并发模型是与 JVM 最大的差别：JVM 的基本单位是线程（线程池随手开）；Node 的 JS 侧是单线程 + 事件循环——所有 IO 异步非阻塞（"发起读文件 → 注册回调 → 干别的 → libuv 通知完成"）。要多核才用 worker_threads（真线程，但靠消息传递，用起来像轻量进程）。

Node 事件循环 ≈ Netty 的 EventLoop：单线程跑所有回调，epoll 机制一个线程服务上万连接。JVM 把选择权给你（线程 or Netty 风格），Node 在语言层强制 Netty 风格。这也解释了本仓库全部 async/await 而无锁的原因——单线程事件循环里没有数据竞争，不需要 synchronized。

"系统级能力"从哪来？Node 二进制本身是 C++ 程序，每个能力（fs、net、child_process）都是编译进 node.exe 的 C++ 实现，经 V8 的 C++ 绑定层暴露给 JS。开发者不写 JNI，但 Node 内部处处是"JNI"——这套绑定机制的公开形式就是 N-API（见第三节）。所以"Node 掌握全系统权限"不是特权 API，而是浏览器里被沙箱拦住的绑定，在 Node 里天然向 JS 开放。

二、libuv 事件循环的六个阶段

Node 主线程活着时循环以下六阶段，每阶段一个 FIFO 队列，跑完非空阶段进下一个：

┌─────────────────────────────────────────────────┐
│ timers             setTimeout/setInterval 到期回调      │
│ pending callbacks  上一轮延迟的系统操作回调（TCP 错误等） │
│ idle, prepare      libuv 内部簿记                       │
│ poll     ★核心：等 IO（epoll/IOCP）；有 timer 快到期时    │
│          会算阻塞上限，避免睡过头                          │
│ check              setImmediate 回调                    │
│ close callbacks     关闭完成清理（socket.destroy 后通知）   │
└─────────────────────────────────────────────────┘
每轮结束检查活跃 handle/请求；全空闲且无待办 → 进程退出

实用结论：setImmediate（check 阶段，本轮 IO 后）先于 setTimeout(0)（timers 阶段，下轮才轮到）。微任务（Promise）不在这六阶段里，在每个宏任务之间插队执行。

poll 阶段 = Netty 的 selector.select(timeout)，timeout 由最近 timer 算出——完全同构，只是 Node 把"runAllTasks + select"细化成了六个有名有姓的队列。

三、N-API：Node 世界的 JNI

从 JS 调 C/C++ 代码的机制，流程是 Java JNI 的翻版：

写 C++ 源码（用 N-API 稳定 C ABI 头文件）
  ↓ node-gyp 构建工具（读 binding.gyp 配置 —— ≈ 精简版 CMake）
  ↓ 调平台编译器（Windows: MSVC / Linux: gcc）
  ↓ 产出 .node 文件（本质 = 改了扩展名的 DLL / .so）
  ↓ JS 里 require('xxx.node') → V8 注册成 JS 可调对象

关键演进：早期 API（NAN）跟着 V8 版本变，每升 Node 全部 addon 重新编译；N-API 承诺 C ABI 永久稳定——编译一次，任何后续 Node 版本都能加载，addon 生态才立住。现代分发用 prebuildify/node-pre-gyp 预编译各平台二进制随包发布，用户免本地编译（Windows 没装 MSVC 也能装）。

binding.gyp ≈ CMakeLists；N-API ≈ JNI 的稳定 ABI 化（比 JNI 做得好的地方：Java 每 JDK 大版 JNI 行为也会抖）。MyDSH 仓库 native/ 的 @deepseek-ai/node-addon-system 就是这么编的；Electron 比纯 Node 多出的窗口/托盘/菜单能力，本质也是一批内置 addon。

四、执行模型与性能：V8 就是 Node 的 HotSpot

不是"类 JIT 的解释执行"——就是真 JIT，且 V8 是工业界最强 JIT 之一。分层执行（与 HotSpot 同源思想）：

Ignition   解释器：字节码逐条解释 —— 冷代码，启动快
Sparkplug  基线 JIT：快速出未优化机器码
Maglev     中阶 JIT：较激进优化
TurboFan   顶层 JIT：类型反馈 + 推测优化 → 高质量机器码
           热函数逐级"加热"上升；推测失败（类型变了）→ 去优化回退

性能的真实图景：

场景vs 原生（C++/Rust）
纯数值计算、序列化热循环慢 2~10 倍（Deopt、GC、隐藏类等差距真实存在）
IO 密集（网络服务、agent 负载）几乎无差：瓶颈在网络/磁盘等待，JS 只做编排；事件循环吞吐常胜 JVM 线程池（免线程切换）
真有 CPU 热点下沉 C++ addon 兜底（VS Code / 本仓库 native addon 的做法）

agent harness 恰好是 IO 密集的极端形态：一次对话 = 等模型流（秒级）→ 等工具进程 → 等磁盘，V8 只做"调度和拼 JSON"。这也是 TS 生态能撑起 VS Code/Cursor 这类大型软件的原因：性能瓶颈都不在 JS 执行层。

五、Electron：带后端的定制浏览器

Electron = 把 Chromium + Node.js 打包成一个可执行程序框架。你直觉里的"超级 webview"是对的——但带了一个全权限后端。与浏览器同为 Chromium 技术但模型不同：

┌─ 主进程 (Main) ──────────────────────┐
│  Node.js 全系统权限                     │
│  MyDSH: apps/desktop/src/main.ts        │
│  管：窗口生命周期、菜单、协议、托盘、更新    │
└──────────┬───────────────────────────┘
           │ IPC（JSON 消息进程间通信）
┌─ 渲染进程 (Renderer) ────────────────┐
│  Chromium 沙箱 = "浏览器标签页"           │
│  加载 apps/web 的 React 产物             │
│  无 fs/进程权限，干活必须 IPC            │
└─────────────────────────────────────┘

MyDSH 在标准模型上再加一层成三层：渲染（React UI）+ 主进程（窗口/更新/单实例）+ Host 进程（主进程以 ELECTRON_RUN_AS_NODE=1 拉起的纯 Node 子进程，跑整个 Cordis 插件树、开本地 HTTP server）。UI 不含业务逻辑，全靠认证 RPC 连 Host。

双进程模型 = Android 双进程（前台 UI + 后台 Service 经 Binder）= Flutter Platform Channel（UI 进程不直接碰系统 API）。Electron 主进程 ≈ Application/Service 层，renderer ≈ Activity 层。入口查找规则：Electron 读 package.json 的 "main"；CLI 读 "bin"；src/index.ts 只是包的库导出面（facade），不是程序入口——找入口看 package.json，找包的 API 看 src/index.ts。

六、contextBridge：被远程网页打出来的安全边界

历史教训：早期 Electron 应用图省事开 nodeIntegration: true——渲染进程（跑不可信内容的层）拥有全套 Node 权限。应用加载任何带 XSS 的页面，攻击者注入的 JS 就能 require('child_process') 格式化硬盘。2016 年前后一批知名应用真实中招。

contextBridge 是架构级亡羊补牢，原则 权限进不了不可信环境：

  • renderer 开 sandbox（纯 Chromium，0 Node 权限）
  • preload 脚本 = 有 Node 权限的唯一小岛
  • contextBridge.exposeInMainWorld('api', {...}) 把精选的几个函数以纯函数桥挂给网页世界：参数/返回值结构化克隆，函数引用、原型链污染全过不了桥
= Android 的分层：网页 = App 层（无特权），preload = Binder 桥接层（白名单方法表），主进程 = System Service 层。MyDSH 更极端——渲染进程只连 Host 的 RPC server，主进程仅做窗口管理，业务面最小暴露。

七、pnpm：更快且省磁盘的 Maven

pnpm = performant npm，Node 的包管理器（npm 生态 ≈ Maven 仓库生态）。npm 包没有编译环节，包管理器的职责就是"解析版本依赖图 → 下载 → 摆成可 import 的目录"。

npm 的历史包袱：每项目独立 node_modules 副本（磁盘爆炸）+ 依赖拍平（幽灵依赖——用了没声明的包也能跑，换个环境就崩）。pnpm 三板斧：

  1. 内容寻址全局 store：所有包全机只存一份，按内容 hash 索引；安装 = 硬链接（同一文件磁盘只有一个物理副本）
  2. 严格隔离：node_modules 用 symlink 树，只能 import 声明过的依赖，杜绝幽灵依赖
  3. 原生 workspace：根 pnpm-workspace.yaml 声明 monorepo 成员，成员间依赖写 "@deepseek-ai/dsh-session": "workspace:*" 直接 symlink 到本地目录，发布时才替换为真实版本
全局 store = Maven 的 ~/.m2/repository（Maven 用户秒懂），只是 pnpm 多用硬链接让项目目录看起来仍完整；workspace:* ≈ implementation(project(":dsh-session"))；pnpm-lock.yaml ≈ 版本锁定文件；package.json 的 scripts 段就是 Node 生态的构建系统（没有 Makefile/Gradle wrapper 概念）。

本仓库常用命令：

pnpm install                  # 装全部工作区依赖（= mvn install 的大头，一次即可）
pnpm run build                # 构建全部包
pnpm --dir apps/desktop run package:win:x64:unsigned   # 在指定包目录跑脚本
pnpm dsh --profile web "任务"  # 跑根 package.json 定义的 dsh script
pnpm why <包名>               # = mvn dependency:tree

与内网环境的关系：pnpm 默认只认 HTTPS registry，我们改了 desktop-release-environment.mjs 接受公司 HTTP 私服；下载走 Node fetch 需信任 MITM 证书（NODE_EXTRA_CA_CERTS）——打包时的全套环境变量就是伺候这条链路。
